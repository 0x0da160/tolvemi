# §18.1c 追加分の計数規則：設計案

> **状態：承認済み（D1 は A、D2 は上限の新設、2026-10-14）。** 規則 G と規則 L を実装し、代表 program の値を `crates/tlvm/tests/counting.rs` で固定した。spec `spec/lptl-v1/LPTL_design_v1.md` の §18.1c は、この設計の基礎と規則に差し替えた。§18.1c は G0 の未達項目のままである（未了の項目は spec §18.1c の末尾）。

対象は v1.1〜v1.16 の追加分の型検査の論理仕事量（SemanticWork）と、§18.3 の実行の参照イベントとの対応。

## 1. 結論

1. **型検査の計数は、型検査器が読む木で数える（書換えの前）。** 書換え（`hof::lower`・`dict::erase`・`sums::lower`・`records::lower`）は型検査の計数に入れない。spec の現文「接着部分の書換え後のプログラム」は、型検査については実装と合わない。
2. **実行の計数（§18.3）は、評価器が動かす書換え後の木で数える。** 書換えの形は Steps と AllocatedNodes を決めるので、形を trace fixture で固定する。型検査の規則とは別の段の規則である。
3. **総称の単相化は規則 G で数える。** 宣言の形の検査（第一パス）に、使われた型引数の組ごとの複製の本体の検査を足す。現在は第二パスの総計だけを報告しており、未使用の総称の関数と型引数の具体化を落としている（§5）。
4. **規則 L：`loop` の結果型 `Option<S>` は、初期値・最大回数・本体がすべて正常なときだけ数える。** 現在は、最大回数や本体が誤りでも一つ数える（§6）。
5. **印つきの写し（v1.15）は現行どおり。** 受理時は印なしの写しの仕事量、拒否時は印つきの写しの仕事量を報告する。
6. **再帰する直和型（v1.14）は、検査の前に補助関数を加えて書き換えるので、その補助関数も宣言として数える。** 形は fixture で固定する（§4.3）。

実装の変更が要るのは規則 G と規則 L の二点だけで、ほかの節点の規則は現在の実装と一致する（§2）。

## 3. 計数の基礎

### 3.1 型検査の木（規則 R）

型検査器（`checker.rs` の `check_program_with`）が読む木は、次の順に作られる（`api.rs` の `expand_with`・`compile_expanded`、`generics.rs` の `check`）。

1. 名前の検査。
2. 型引数の解決（`generics::resolve`）。
3. 再帰する直和型の書換え（`recursive::expand`）。構築・`match`・型名を補助関数と構成子の関数の呼び出しに直し、それらを宣言に加える（v1.14）。
4. 直和型の展開（`sums::expand`）。構築は `ok`／`err` の入れ子（`Inj`）、`match` は `SumMatch` のまま残す。
5. レコードの展開（`records::expand`）。構築は `pair` の入れ子、型は pair の別名。`Field` は残す。
6. 第一パス：全関数を検査する。総称の関数は宣言の形のまま。
7. 総称の単相化と第二パス（§5 の規則 G）。

型検査の後の書換え（`hof::lower`・`dict::erase`・`sums::lower`・`records::lower`）と、検証済み部品の検査は、型検査の計数に入らない。検証済み部品は論理仕事量を数えない。展開で生じた節点（`Inj`・`pair`・`Field` など）は、それぞれ Visit を一つ数える。

### 3.2 実行の木（規則 E）

評価器は書換え後の木を動かす（`compile_expanded` の書換えたテキストを検証済み部品が検査し、その `verified` を実行する）。§18.3 の参照イベントは、この木に適用する。したがって、`hof`・`dict`・`loop`・`match`・`records` の書換えの形は、Steps と AllocatedNodes を決める。形は trace fixture で固定する。

### 3.3 印つきの写し（規則 T）

- 印つきの写し（v1.15、`compile_nominal`）が受理されたら、報告は印なしの写しの仕事量。拒否されたら、報告は印つきの写しの仕事量（現行どおり）。
- 受理時に二つの写しの trace が一致することは、読みでは確認した範囲にとどまる（§7 の O-3）。fixture で確かめる。

## 4. 節点ごとの規則

§18.1a と同じ書式。共通の規則は次のとおり。

- Visit は式の節点ごとに一つ。組込みと呼出しは、引数をすべて左から検査してから、比較と構成を行う（実装の順）。
- Head と Equal は §18.1a の定義どおり（Equal は構造的。根の構成子対に一イベント、子を左から比べ、最初の不一致で止める）。
- BuildType は、子と制約が正常なときだけ、表の順に発行する。
- ErrorType の子を持つ節点は、BuildType も比較も発行しない（0）。

### 4.1 リテラル・組込み

| 節点 | 比較と構成の順（引数は検査済み） | BuildType |
|---|---|---|
| 整数・bool・unit のリテラル | — | 型一つ 1 |
| 文字のリテラル | — | Char 1 |
| 文字列のリテラル | — | Char、List<Char> の順に 2（長さによらない） |
| `code(c)` | Equal(c, Char) | Int 1 |
| `char(n)` | Equal(n, Int) | Char、Option<Char> の順に 2 |
| `to_string(n)` | Equal(n, Int) | Char、List<Char> の順に 2 |
| `parse_int(s)` | Equal(s, List<Char>)（構造的に 2） | Int、Option<Int> の順に 2 |
| `add`・`sub`・`mul`・`min`・`max` | Equal(a, Int) → Equal(b, Int) | Int 1 |
| `neg` | Equal(a, Int) | Int 1 |
| `lt`・`le` | Equal(a, Int) → Equal(b, Int) | Bool 1 |
| `eq` | Equal(a, b) | Bool 1 |
| `mod`・`div` | Equal(a, Int) → Equal(b, Int) | Int、Option<Int> の順に 2 |
| `range(a, b)` | Equal(a, Int) → Equal(b, Int) | Int、List<Int> の順に 2 |
| `contains(xs, v)` | Head(xs, List) → Equal(v, 要素型) | Bool 1 |
| `sort(xs)` | Equal(xs, List<Int>)（構造的に 2） | 0 |
| `length(xs)` | Head(xs, List) | Int 1 |
| `reverse(xs)` | Head(xs, List) | 0 |
| `cons(v, xs)` | Head(xs, List) → Equal(v, 要素型) | 0 |
| `concat(a, b)` | Head(a, List) → Head(b, List) → Equal(両方の要素型) | 0 |
| `uncons(xs)` | Head(xs, List) | Pair<A, List<A>>、Option<…> の順に 2 |
| `fst(p)`・`snd(p)` | Head(p, Pair)。名義の型は比較せず拒否（0） | 0 |
| `some(v)`・`pair(a, b)` | 両方の子が正常なとき | Option 1・Pair 1 |
| `none<T>()`・`list<T>(…)` | list は各項を要素型と Equal（項はすべて検査済み） | Option 1・List 1 |
| `dict<K, V>()` | — | Dict<K, V> 1 |
| `dict_from(xs)` | Head(xs, List) → Head(要素, Pair) | Dict<K, V> 1 |
| `dict_get(d, k)`・`dict_has(d, k)` | Head(d, Dict) → Equal(k, K) | Option<V>・Bool 1 |
| `dict_put(d, k, v)` | Head(d, Dict) → Equal(k, K) → Equal(v, V) | 0 |
| `dict_remove(d, k)` | Head(d, Dict) → Equal(k, K) | 0 |
| `dict_size(d)` | Head(d, Dict) | Int 1 |
| `dict_keys(d)`・`dict_values(d)` | Head(d, Dict) | List<K>・List<V> 1 |
| `dict_entries(d)` | Head(d, Dict) | Pair<K, V>、List<Pair<K, V>> の順に 2 |

`dict_*` は型検査の後に `fold` などへ書き換えられる（`dict.rs`）。この表は書換え前の呼出しを数える（規則 R）。

### 4.2 直和型・Result・match

| 節点 | 比較と構成の順 | BuildType |
|---|---|---|
| `ok<T, E>(v)`・`err<T, E>(v)`（`Inj` の一段） | Equal(v の型, 対応する成分) | Result<T, E> 1 |
| `match_option(m, n, 引数 x の本体 s)` | 検査：m、n → Head(m, Option) → s → Equal(s, n) | 0 |
| `match_result(m, ok 枝 a, err 枝 b)` | 検査：m → Head(m, Result) → a → b → Equal(b, a) | 0 |
| 直和型の `match`（`SumMatch`） | 検査：対象 → 対象の型の確認（直和型は Equal、総称は bind、Result・Option 族は Head）→ 各枝を検査した直後に、最初の正常な枝と Equal（構造的） | 0 |
| 族が決まらない `match`（`MatchKind::Any`） | 検査：対象 → C 一つ（直和・Result・Option のどれでもなければ拒否）→ 枝（上と同じ） | 0 |

直和型の構築は、変種の位置に応じた `Inj` の入れ子になる（`sums::expand`）。変種 k の構築は、入れ子の段ごとに上の `Inj` の規則で数える。

### 4.3 レコード・再帰する直和型

- レコードの構築は展開後の `pair` の節点として数える。n 項のレコードは n − 1 個の pair 節点で、各節点は Visit 一つと Pair 一つ（子が正常なとき）。
- `e.f`（`Field`）：検査 e → Equal(e の型, レコード型)（総称は bind）。名前の違うレコード型は比較せず拒否（0）。BuildType はない（結果は展開された型の成分を参照する）。
- 再帰する直和型（v1.14）：構築は構成子の関数の呼び出し、`match` は `if` の連鎖と補助関数（`rec_at`・`rec_take`・`rec_drop` など）の呼び出しになる。これらは非総称の呼び出しとして数え、補助関数の本体は宣言として各一度数える。形は v1.14 の差分仕様と fixture で固定する（§7 の O-2）。

### 4.4 関数を取る組込み（`map` など）

| 節点 | 検査と比較の順 | BuildType |
|---|---|---|
| `map(xs, 引数 x の本体 e)` | 検査：xs → Head(xs, List) → e | List<B> 1（e が正常なとき） |
| `filter(xs, p)` | 検査：xs → Head → p → Equal(p, Bool) | 0 |
| `any`・`all` | 同上 | Bool 1 |
| `find` | 同上 | Option<A> 1 |
| `sort_by(xs, k)` | 検査：xs → Head → k → Equal(k, Int) | 0 |

### 4.5 `loop`（規則 L を含む）

| 節点 | 検査と比較の順 | BuildType |
|---|---|---|
| `loop(init, max, 引数 s の本体 e)` | 検査：init → max → Equal(max, Int) → e → Equal(e, Option<S>)（根の対と中身の構造で数える） | Option<S> 1（init・max・e がすべて正常なとき、比較の後に） |

### 4.6 呼出し

- **非総称の呼出し。** 引数をすべて検査 → 各実引数を宣言の型と Equal（左から）→ 戻り型は参照（0）。個数が違えば、比較せず拒否する（引数の検査は続ける）。
- **総称の呼出し。** 引数をすべて検査 → 個数の確認（違えば 0 で拒否）→ 各実引数を型パターンと bind（左から）→ 推論できない型引数があれば 0 で拒否 → 型引数の数だけ BuildType 一つ（明示した型引数も推論したものも、順に）→ 戻り型に BuildType 一つ。
- **bind(p, t)。** p か t が ErrorType なら 0。p が型変数なら Compare を一つ数える。その型変数が既に束縛されていれば、その束縛と t を Equal で比べ、この Equal も数える（Compare と Equal の両方を数える。2026-10-15 にオーナーが決定）。p が型変数を含まないなら Equal(p, t)。p が型変数を含む構成子なら Compare 一つ（構成子か子の数が違えば拒否）、子を左から bind する。

## 5. 総称の単相化（規則 G）

§18.1a は「非選択枝・未到達関数も静的に検査する」と定める。総称の関数も、使われなくても宣言の形で一度検査し、数える。現在の報告は第二パスの総計だけなので、未使用の総称の関数（§2 の 3）と、型引数の具体化の BuildType が落ちる（§2 の 10）。

提案：

- **第一パス。** 全関数を宣言の形で検査する。総称の関数は型変数を不透明な型として扱う。総称の呼出しの型引数と戻り型の BuildType は、この第一パスで数える。
- **第二パス。** 使われた型引数の組ごとの複製の本体だけを数える。非総称の関数は、第一パスで数えたものを数え直さない。
- **報告値は第一パスと第二パスの和。** 上限は、この和が 2,000,000 を超えるイベントの直前で検査する。超過の位置は、元の総称の本体の span で報告する（現在と同じ）。

数の例：§2 の 3 は、第一パス 4（g の本体 2、f の本体 2）で 4。§2 の 10 は、第一パス 8（id の本体 2、f の 6）と複製 `id` の本体 2 の和で 10。

この規則は、「二つのパスは実装の内部の再検査であり、計数に入れない」という §18.1a の原則と両立させる。非総称の関数を二度数えないのはそのためである。

## 6. `loop` の BuildType（規則 L）

`loop` の結果型 `Option<S>` は、init・max・本体がすべて正常なときだけ一つ数える。本体と `Option<S>` は Equal で比べる。この比較の数は、Head(本体, Option) と Equal(中身, S) の組と同じである（根の対に一つ、中身の構造で数えるため）。実装も、`Option<S>` の BuildType を作らずに本体と比べ、正常なときだけ BuildType を最後に数える。

- 正常な入力では、報告される数は変わらない（BuildType と比較の総数が同じ）。trace の順は変わる（BuildType が比較の後に来る）。
- 誤りのある入力では、現在より BuildType が一つ減る。§2 の 4 は 10 から 9 になる。

## 7. 残る論点

- **O-1　書換えの深さによる拒否。** `compile_expanded` は書き換えたテキストを検証済み parser に通し、式の深さが上限を超えると `E-LIMIT-STATIC-EXPR-DEPTH` で拒否する（`api.rs` の `cross_check_at`）。元の式の深さが上限内でも拒否されうる。spec の表にない。読みによる確認で、測定はしていない。書換えの深さの上界を §18.1 に書くか、この拒否を仕様に書く必要がある。
  - **状態（2026-10-14）：** 決定（推奨の案を、オーナーが 2026-10-14 に選んだ）。§18.1 に書いた。上限は増やさない。
- **O-2　再帰する直和型の補助関数。** 補助関数と構成子の関数は宣言として数える（`recursive.rs` の `ctor_fn`・`helpers`。読みによる確認）。形が差分仕様で固定されているかは未確認。
  - **状態：** 固定した。構築子・match・補助関数の全文を `crates/tlvm/tests/recursive.rs` の `recursive_helper_shapes_match_the_deltas` で固定した（補助関数の本体は仕様に文字として書いていない）。
- **O-3　印つきと印なしの trace の一致。** 受理時は印なしの写しだけを報告する。二つの trace が一致することは未確認。fixture で確かめる。
  - **状態：** 一致しない。代表 program で、印つきは 472、印なしは 356。差は印の型と `tree_flat` の呼出しによる。受理時の報告は印なしの写しなので、一致は報告値に要らない（規則 T）。`counting.rs` の `tagged_copy_is_reported_only_when_rejected` で固定した。印つきの構築の形は、v1.15 差分 §3 の `<名前>_wrap` の文言と違う。この形を正とすることを、オーナーが 2026-10-14 に選んだ（DECISION-15）。この数はその形に依る。
- **O-4　実行の整数の bit 数。** `RunResult::Completed` には `steps` と `allocated_nodes` だけが出ている（`evaluator.rs`）。整数の bit 数は取り出せない。取り出し方を決める必要がある。
  - **状態：** 決定（推奨の案を、オーナーが 2026-10-14 に選んだ）。成功した run の結果には bit 数を含めない。上限の検査は評価器の割当ごとと入力の検査で行う（検証済みの評価器の `IntegerBits`）。取り出しを足すには評価器と Verus の再検証が要る。
- **O-5　族が決まらない `match`。** `MatchKind::Any` が受理される経路（`_` だけの `match` など）があるかは未確認。
  - **状態：** 到達する。`match x { _ => 0 }` は、型 `T = A | B` と `Option<Int>` の両方で受理される（`sums.rs` の `wildcard_only_match_is_accepted_on_sums_and_options`）。v1.4 の「`_` は残りをまとめる」に従う。
- **O-6　版の扱い。** v1.11（import）と v1.16（パッケージ）は、連結後の一つの木を数える（規則 R の範囲）。v1.12（比較 cache）は計数を変えないことを `tests/sharing.rs` で確かめ済み。v1.13 は言語を変えないので、計数の規則を足さない。
- **O-7　書換え後の大きさ（増幅）。** 解決（2026-10-14、DECISION-13）：`E-LIMIT-STATIC-REWRITTEN-BYTES` を新設した（4,194,304 bytes。型検査を通ったプログラムの、検証済み部品へ渡す文字列）。計測：2.2 MB の書換えは約 2.7 秒で受理、4.4 MB は上限により拒否。増幅の例：loop を 400 個並べると原文 24,356 バイトが書換え後 1,077,083 バイト（約 44 倍）になる（§11）。拒否までの時間も同日に解決した：sums・records・dict の書換えと整形のうち、書換えを要するものだけを複製せずに行うようにした。約 9 MB の書換えの拒否は、以前の約 11 秒から 16 秒が約 1 秒になった（release、800 関数、loop 3,200 個）。出力は計測の前後でバイト単位で同じである。

## 10. 決めてもらうこと

- **D1　型検査の木。** 【決定】入力の木（A）を、オーナーが 2026-10-14 に選んだ（DECISION-12）。以下は決める前の記述である。入力の木（推奨）か、書換え後の木（spec の現文）か。推奨の理由は、現在の実装と一致し、接着部分の書換えを変えても型検査の数が動かないこと。実行は、どちらを選んでも書換え後の木で数える。
- 規則 G と規則 L は、§18.1a の「静的に検査する」と「子と制約が正常なとき」の原則に従うので、推奨として書いた。
- 二択の利点・欠点・リスクの詳細は §11。推奨は A（入力の木）のままである。A を選ぶなら、書換え後の大きさの上限を次の決定として出す（O-7）。

## 11. D1 の二択の比較（詳細）

計測は 2026-10-14、コミット 4349127 の実装に対する一時テスト（各 1 回。コミットしていない）。「入力の木」は型検査器が読む木（A の数）、「書換え後の木」は `hof::lower`・`dict::erase`・`sums::lower`・`records::lower` の後のプログラムを、同じ検査器で数えた値（B の数）。

| プログラム | 入力の木（A） | 書換え後の木（B） | 備考 |
|---|---:|---:|---|
| `map(x, \|y\| add(y, 1))` | 13 | 22 | 書換え後は `reverse`・`fold`・`cons` |
| `filter(x, \|y\| lt(y, 2))` | 13 | 28 | |
| `sort_by(x, \|y\| y)` | 7 | 170 | 挿入整列の fold の入れ子 |
| `loop(x, 3, \|s\| none<Int>())` | 12 | 714 | 16 段の入れ子。書換え後の文面は約 2.6 KB |
| `dict_get(dict_put(dict<Int, Int>(), 1, x), 1)` | 17 | 125 | |
| 記録の参照 `p.x` | 6 | 4 | 書換え後は `fst` で、比較が少ない |
| 直和型の `match` | 10 | 10 | 合計は偶然同じ。内訳は違う（visit 4→6、compare 5→3） |
| 拒否された `map`（引数の型違い） | 9 | 9 | 書換えは途中で止まり、文面に `map(` が残る |

増幅（loop を並べたプログラム、受理までの時間は release）：

- 100 個：原文 6,056 バイト → 書換え後 260,711 バイト（約 43 倍）、0.31 秒。
- 400 個：原文 24,356 バイト → 書換え後 1,077,083 バイト（約 44 倍）、1.83 秒。
- 見積もり（未測定）：原文の上限 1 MiB と AST の上限 131,072 節点から、loop は約 13,000 個まで入る（一つの関数は約 10 節点）。書換え後は約 34 MB になり、時間は数十秒から数分の見込み。

### 11.1 A：入力の木で数える（推奨）

利点：

- 現実装と一致する。15 件のうち 12 件は規則から手で予測した値と一致し、残り 3 件は規則 G と規則 L の実装修正だけで直る。
- 数を手で検算できる。fixture の期待値を、書換えの実装を走らせずに規則の表から確かめられる。
- 接着の後段（`hof`・`dict`・`sums`・`records` の書換え）を変えても、型検査の数と受理の境界は動かない。接着は版ごとの意味の一致が未証明（§11.2a）なので、この独立性には価値がある。
- 数は、Rust の検査器が実際に仕事をする木の数である。上限の意味が検査器の仕事量に近い。

リスク・欠点：

- spec §18.1c の「書換え後」を型検査については改める。仕様の契約を変える決定が要る。
- 書換えの大きさは数に入らない。増幅（上の計測）を抑える上限が今はない。A を選んでも、書換え後の大きさの上限を新しい静的上限として別に決める必要がある（O-7）。
- 追加分の規則表（約 40 行）を実装が正確に従う必要がある。規則 G と規則 L は実装の変更が要る。
- 再帰する直和型の補助関数は入力の木に入るので、この数は補助関数の形に依る（O-2）。A でも接着から完全には切り離せない。
- 数は検証済み部品の仕事量を直接は表さない。部品側の大きさは、書換え後の文字数（2^28）と式の深さで抑える。

### 11.2 B：書換え後の木で数える（spec の現文）

利点：

- spec §18.1c と §18.3 の現文と一致する。仕様の文言を変えずに済む。
- 数が、検証済み部品が検査し実行する木の数になる。書換え後の式の節点は、どれも少なくとも一つの Visit を数えるので、書換え後の節点数は上限 2,000,000 に抑えられる。増幅も上限で止まる（loop は約 2,800 個で、書換え後は約 7 MB）。
- 型検査と実行の数の土台が一つになる。
- 将来、検証済み部品の側で数の関数を証明する道が開く（今はその仕組みがない）。
- 追加分に専用の規則表がほぼ要らない。核の規則（§18.1a）を書換え後の木に当てればよい（総称の規則を除く）。

リスク・欠点：

- 二段の検査になる。書換えは検査で得た型（`hof::lower` の `HofTypes`）を使うので、入力の木の検査は書換えの前に必ず走る。その仕事量にも上限が要るので、入力の木の数も残る。どちらの数を上限に使うかを決め直す必要がある。
- 拒否されたプログラムは書換えが途中までしか入らない（計測：拒否された `map` の文面に `map(` が残る）。拒否の数（上限超過を含む）の決め方を別に定める必要がある。上限超過は拒否なので、この欠点は中心に当たる。
- 受理の境界が接着の形に依る。接着を効率化したり再証明したりすると、既存のプログラムの受理が変わりうる。接着は未証明なので、未証明の形を規範にすることになる（G3 の境界が広がる）。
- 数が大きく動く。loop は 12 から 714（約 60 倍）、sort_by は 7 から 170 になる。上限に届く loop の数は、約 16 万個から約 2,800 個に変わる。
- 総称の規則は残る。未使用の総称の関数は単相化の後の木に入らない（`generics.rs` の `monomorphize`）ので、書換え後の木では数えられない。
- fixture の期待値を人が検算できない。loop 一つの書換え後の木は約 2.6 KB で、数は書換えの実装を走らせないと出ない。
- 実装の作業量が大きい（検査の二段化、拒否時の規則、計数の配線）。

### 11.3 どちらを選んでも残るもの

- 再帰する直和型の補助関数の形（O-2）。
- 印つきと印なしの trace の一致（O-3）。
- 書換え後の式の深さによる拒否（O-1）。
- 実行の数（Steps・AllocatedNodes）は書換えの形で決まる。両案とも、書換えの形を fixture で固定する必要がある。
- 総称の規則 G。未使用の総称の関数を数えるには、どちらの案でも別の規則が要る。

### 11.4 推奨と次の決定

- 推奨は A のままである。ただし、A は書換え後の大きさを抑えない。現在の実装もそうで、計測では約 44 倍の増幅があり、見積もりでは 1 MiB の原文から約 34 MB の書換え後の木ができる。A を選んだら、書換え後の大きさの上限を次の決定として出す。
- B を選ぶなら、拒否されたプログラムの数の決め方と、二段の検査の設計を先に決める。
- 次の決定（書換え後の大きさの上限）は、上限を新設（推奨）で決まった（DECISION-13）。拒否までの時間（O-7）も同日に解決した。
