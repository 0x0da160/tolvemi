# 既知の注意点

この節は、凍結前の確認で分かった注意点を一か所にまとめる。確認日は 2026-10-14。各項目は、設計書の行、ソースやテストの場所、または実行結果で根拠を示す。仕様どおりの振る舞いは「仕様どおり」と書き、範囲外・未対応・未検査のものは、その旨を書く。

## 仕様どおりだが驚きやすい振る舞い

- **Dict の等値は挿入順を含めて比べる。** 同じ鍵と値でも、入れた順が違えば `eq` は `false` を返す。設計書の `eq` の規則（548 行）による。確認：`dict_put` の順を変えた二つの辞書を `eq` で比べると `false`、同じ順なら `true`。
- **`div(a, b)` は除数が 0 以下なら `none` を返す。** 設計書の定義（541 行）による。確認：`div(x, 0)` と `div(x, -2)` の plain 出力は `null`（`none`）。
- **`rec` の印を付けた関数を含むプログラムは、停止を保証しない。** 印のないプログラムは必ず停止する（設計書 15 行）。

## 範囲外・未対応・未検査

- **`tlvm exec` の entry の入力型は五つの形だけ。** `String`、`List<String>`、`Pair<List<String>, String>`、`Dict<String, String>`、`Dict<String, Int>`。ほかの型の entry は `UnsupportedEntry` になり、JSON の envelope と終了コード 64 を返す（`main.rs` の `exec_cmd`、`runtime.rs` の `ENTRY_SHAPES`。確認：`Int` の entry で終了コード 64）。
- **`exec` で Dict を受けるのは、標準入力の行（`key<TAB>value`）から作る形だけ**（v1.13。`runtime.rs`）。
- **パッケージは、ローカルのディレクトリの依存だけ。** レジストリからの取得、版の範囲指定と解決、ロックファイルは含まない（[v1.16 差分仕様](../../spec/lptl-v1.16/LPTL_v1.16_delta.md) の §0。草案で、`crates/tlvm/src/packages.rs` に実装）。取得と版の解決は v1.0.0 の対象外（下の「決定と未決」を見る）。
- **import は根のディレクトリの内側のファイルだけ。** `..` で根のディレクトリより上へは出られない（v1.16 差分仕様の §0、v1.11 の規則）。
- **多倍長整数の `div_pos` は信頼仮定。** 検証済みの核の外にあり、設計書 925 行が明記している。
- **整数の bit 数は、成功時の結果に含まない。** bit の上限を超えたときは `ResourceExhausted`（`IntegerBits`）になり、そのとき超えた bit 数を報告する（設計書 §18.3）。
- **書換え後の式の深さは、上限 256 で検査する。** `loop` を 20 段入れ子にすると、書換え後の深さは 522 になり、`E-LIMIT-STATIC-EXPR-DEPTH` で拒否される（設計書 §18.1、`crates/tlvm/tests/rewritten.rs`）。
- **`stack_bytes` の超過は未検査。** [必須回帰テスト](../conformance/regression-tests.md) の行 35 では、ref-slot の上限は検査するが、stack_bytes の超過は検査していない。
- **全部の field を書いた `..base` は拒否する（DECISION-21。2026-10-15 に修正）。** 以前は `R { a: x, b: 2, ..undefined_name }` と `R { a: x, b: 2, ..true }` が通った。`records.rs` が base を名前解決も型検査もせずに捨てていたためで、v1 の規則に反する不具合だった。今は `E-RECORD-BASE-REDUNDANT` で拒否する。この拒否では base の中の誤りは報告しない（`..base` を外すと報告される）。レコードの証明の試作（`verus/src/records_proof.rs`）は、この形を前提から外している。

- **検証済みの経路は、記録と名前だけのプログラムに限る（2026-10-20）。** 範囲は `route_scope`（`crates/tlvm/src/api.rs:779–785`）。総称、直和型、再帰する型、`Dict`、hof（`map`・`filter`・`any`・`all`・`find`・`sort_by`。`crates/tlvm/src/hof.rs:72–78`）、`loop` を外す。hof を含むプログラムは、記録・直和型・再帰・総称・`Dict`・`loop` を含まないものに限り、源の文字列を検証済みの経路に通す（2026-10-27、DECISION-43。`route_scope_hof`）。その核の意味が源の意味（xeval）に等しいことは hof-meaning が示す（入力が入口の型を持つこと、署名に Dict が無いことを仮定）。源の文字列の名前の解決が意味を保つことは未証明。範囲の外は従来の経路（ゲートと糖衣の IR）で判定する。`fold` は範囲に入る（核の形。設計書 454、473 行）。
- **末尾のコンマの記録の式（`P { a: x, }`）は構文で拒否する（2026-10-20、オーナーの決定）。** 信頼側の構文器が拒否する（`crates/tlvm/src/parser.rs:937`。設計書の record_items に合わせた）。検証済みの文法も同じく拒否するので、この形は経路に届かない。宣言の末尾のコンマ（`type P = { a: Int, b: Int, }`）は受理し、経路に入る（`crates/tlvm/tests/record_names.rs:379`）。
- **突き合わせは、受理と拒否の別だけを比べる（2026-10-20）。** 符号・位置・理由は比べない（`crates/tlvm/src/api.rs:451`、`541–542`）。型の拒否は調べない（片方向）。展開段階の名前の 8 符号（`api.rs:756–765`）の拒否だけを、検証済みの解決器が受理するかで調べる。`E-SUM-NAME-CONFLICT` と `E-SUM-DUPLICATE-CTOR` は検証済みの側に規則がなく（`api.rs:750`）、突き合わせない。名前の診断の符号と位置は信頼する（`crates/tlvm/src/records.rs:606–610`、`sums.rs:176–232`）。
- **印の形は閉じていない。** 経路の中で印は検証済みの表の番号で作るが（`verus/src/resolve.rs:490–493`）、手で組んだ印の形は v1.15 差分仕様 §5 のとおり未決。`Tags::of` の番号と検証済みの番号の一致は証明せず、テスト（V3、S3c）で確かめるだけ。
- **記録の意味の定理は、一つの向きの部分正しさだけ（2026-10-20）。** `resolve_sound`（`verus/src/records_commute.rs:963`）は、記録と名前の式（`Int`、`Bool`、`Unit`、変数、`pair`、字段の参照、記録の構築）だけを扱い、源の意味が値を持つとき、印なしの核の式がその値に評価されることを示す（`verus/src/records_meaning.rs:109` の `rmean`）。`if`、`let`、`fold`、`match_option`、`match_result` などの他の式、逆向き、型付け、印つきは証明していない。印の消去（S4c）も未証明。

## 運用上の注意

- **debug ビルドでは深い再帰の三つのテストを ignore する。** `crates/tlvm/tests/rec.rs` の 202、236、246 行。debug では評価スレッド（1 GiB）が深さの上限より先に溢れるため、release の CI で実行する。
- **テストのスレッドのスタックは 16 MiB。** `.cargo/config.toml` の `RUST_MIN_STACK` で設定している（深い入力の構文解析を `tests/hof.rs` で確かめるため）。

- **式の深さの上限は、release で確かめた（2026-10-20）。** `cargo build --release -p tlvm` のあと、ネストした加算と記録の式を 50、100、200、256、257 段で試し、1000 段と 5000 段も試した。加算は 255 段まで受理し（検査の深さ 256）、256 段で `E-LIMIT-STATIC-EXPR-DEPTH` になる（実際 257）。記録の式（`P { a: …, b: 1 }.a` の入れ子）は 63 段まで受理し、64 段で拒否する（書換え後の深さ 257）。書換え後の深さは段あたり 4 増える（100 段で 401、200 段で 801）。どの段数でも溢れず、拒否は同じ符号だけだった。上限（`crates/tlvm/src/profiles.rs:33`、256）は変えていない。
- **debug ビルドの CLI は、深さ 100 で主スレッドのスタックが溢れる（2026-10-20）。** 加算と記録の両方で終了コード 134 になり、50 段は受理される。参照の HEAD（`9a96889`）の debug も同じ。release は影響を受けない。スタックの大きさは変えていない。

## 確認の範囲

- **Haiku の確認は一題・二回だけ。** 型引数を書かせた課題は 98-adjacent_pairs の一題で、2026-10-13 と 2026-10-15 の二回とも正解した（[v1.10 差分仕様](../../spec/lptl-v1.10/LPTL_v1.10_delta.md) §5）。回数が少ないので、成功率や一般の傾向の主張には使えない。97-batches は型引数を使わずに解かれた。

- **変異の掃引（V7、2026-10-20）。** 記録のプログラム 77 件（経路の 53 件と V7 の 24 件。末尾のコンマの記録 `record_names.rs:383` は除く）に、七種の変異（未知の型、型の重複、字段の重複、字段の削除、`..base` の追加と削除、字段の改名）を掛けた。本番の CLI で 540 件を流し、検証済みの食い違い 0、クラッシュ 0（受理 32、拒否 508）。そのうち名前の 8 符号に当たったのは 430 件。テスト `v7_record_mutations_get_no_verified_mismatch` は偶数番目の 284 件を流す（受理 9、拒否 275、名前の符号 232 件）。変異を一つも作れないプログラムが 5 件ある。
- **宣言の数と書換えの大きさ（V12、2026-10-20）。** テスト `v12_declaration_count_and_rewritten_size_decisions_match_head` は、HEAD（`9a96889` の参照 CLI）と同じ判定を確かめる。200 個の平らな宣言（使うのは `R0` だけ）は、`R126` で型の深さの上限（`E-LIMIT-STATIC-SEMANTIC-TYPE-DEPTH`、期待 128、実際 129）に掛かる（平らな宣言の上限は 126 個。v1.15 差分仕様 §3 に書いた）。鎖の 200 宣言は `R63` で同じ符号になる。書換えの大きさの上限（`E-LIMIT-STATIC-REWRITTEN-BYTES`）は、宣言の数ではなく書換えの量で掛かる（60 段の鎖と `R59` を引数に取る 200 の関数で 5,663,489 bytes）。

## 決定と未決

決定（2026-10-15、オーナー。記録は [設計状態と出荷ゲート](status-and-gates.md) の DECISION-16 から 24）：

- **パッケージの範囲（DECISION-16）**：v1.0.0 は、ローカルの依存だけ。取得と版の解決は対象外と v1.16 差分 §0 に書いた。
- **速度（DECISION-17）**：v1.0.0 の条件に性能の目標は置かない。計測の基準値だけを残す（共有のロードマップ §7 のとおり）。
- **exec の Dict の形（DECISION-18）**：`Dict<String, String>` と `Dict<String, Int>` だけを受ける。v1.13 差分（冒頭の「この版に含めないもの」と §1a）に書いてあり、実装は変えない。設計書は鍵の型を制限していない（119 行）が、exec の入力はこの二つに限る。
- **整形（DECISION-19）**：`tlvm fmt` と LSP の整形は、`check` と同じ検査を通ったプログラムだけを整形する。型の誤りがあれば整形せず拒否する。仕様（v1.12 差分 §2b）と実装を変えた。
- **cargo fmt（DECISION-20）**：別コミット（`56c5ce5`）で全体へ適用した。`cargo fmt --check` は通る。CI の段に fmt は加えていない。
- **全部の field を書いた `..base`（DECISION-21）**：拒否する（`E-RECORD-BASE-REDUNDANT`）。v1.1 差分の名前の規則（「残りを base から写す」）に沿う。
- **G4 の最終評価（DECISION-22）**：秘密の seed は使わず、公開の 99 題とは別の新しい最終課題を作る。課題の中身はリポジトリの外に置き、事前登録はハッシュで行う（未着手）。
- **§11.2a の証明の形（DECISION-23）**：書換えの実装そのものを Verus で検証する（最も強い形）。仕様上の同値の試作は出発点。
- **§11.2a の範囲（DECISION-24）**：v1.1 から v1.16 まで全版を今回の作業に入れる。凍結は §11.2a の後になる。
- **min と max の割当（DECISION-25）**：選んだ引数の値を返すが、結果の整数を一つ割り当てて数える（§8.4、§18.3 の規則 7）。Steps と AllocatedNodes はこれに従う。
- **既に束縛された型変数への bind（DECISION-26）**：Compare と既存の束縛との Equal を両方数える（§4.6）。同じ型変数が二度現れる呼出しは、片方だけを数える読みより比較の数が多い。
- **ok と err の構築（DECISION-27）**：一つのステップと一つの割当を数える（`some` と同じ、§8.4）。
- **§11.2a の形 C の規模（DECISION-28）**：v1.1 で測ってから形を決める。測定の結果が出るまで形は未決。
