# LPTL v1.14 差分仕様：再帰する直和型

本書は [v1.13 差分仕様](../lptl-v1.13/LPTL_v1.13_delta.md) に対する差分である。自分自身を項に含む直和型
（`type Tree = Leaf | Node(Tree, Int, Tree)`）を書けるようにする。

状態：処理系は本書どおりに実装済み。LLM での確認は §10。

**検証済みの中核（`verus/`）は変えない。** 再帰する型は、検査の前に接着部分（`crates/tlvm/src/recursive.rs`）で二通りの写しにする。

- **印つきの写し**：再帰する型の値に、型ごとに違う印を付けた型を与える（`Pair<印, List<Int>>`）。型の区別は、この写しを検証済みの部品が検査して判定する。
- **印なしの写し**：印を外し、再帰する型の値を整数の列 `List<Int>` として扱う。実行はこの写しで行い、検証済みの部品が検査する。

受理されるのは、両方の写しが検証済みの部品に受理されたプログラムだけである。

**この版に含めないもの**：総称（型引数つき）の再帰する型、項に `String`・`List`・レコード・再帰しない直和型を置くこと、
名義の型（型の名前そのものを検査の核に入れること。§4、§9）、木の形の JSON による入出力（§5）。

## 1. 追加するもの

- 直和型の宣言 `type Name = A | B(T, ...) | ...` のうち、宣言の型の名前をたどって自分に戻るもの（再帰する型）。
  相互に参照する型（`type A = X(B) | Ea` と `type B = Y(A, Int) | Eb`）も、循環に入るものはすべて再帰する型になる。
- 項の型の制限（§2）。
- 構築・`match`・型の名前の書き換え（§3）と、印つきの写し（§3a）。

## 2. 型の制限

- 再帰する型の項の型は、`Int`、`Bool`、再帰する型そのもの（引数なし）のどれかでなければならない。
  それ以外（`String`、`List<...>`、`Option`、レコード、再帰しない直和型など）は `E-REC-FIELD-TYPE`。
- 再帰する型に型引数を付けた宣言（`type Tree<T> = ...`）は `E-REC-TYPE-PARAM`。使うときに型引数を書いた
  `Tree<Int>` は `E-TYPE-GENERIC-ARITY`。
- 再帰しない直和型と型の規則は v1.4 のまま（使う前に宣言する）。再帰しない型が再帰する型を項に含むのは構わない
  （`type Wrap = W(Tree) | N`）。
- 名前の規則（構築子の名前の一意性、関数・型との重なり、束縛名との重なり）は v1.4 と同じ診断を出す。

## 3. 値の符号化と書き換え

実行する値（印なしの写し）は `List<Int>` である。構築子 `C` の番号を `k`（宣言の順、0 から）、項を `f1`、…、`fn` とすると、

```
C(f1, ..., fn) = [k] ++ block(f1) ++ ... ++ block(fn)
block(Int の値 x)       = [1, x]
block(Bool の値 b)      = [1, if b then 1 else 0]
block(再帰する型の値 v)  = [length(v)] ++ v
```

引数のない構築子は `[k]`。例：`Leaf` は `[0]`、`Node(Leaf, 3, Leaf)` は `[1, 1, 0, 1, 3, 1, 0]`、
`Node(Leaf, 3, Node(Leaf, 4, Leaf))` は `[1, 1, 0, 1, 3, 7, 1, 1, 0, 1, 4, 1, 0]`。

項の長さを前に置くので、次の項の位置を求めるのに子の中身を再帰で読まなくてよい。書き換えは次のとおり。

- 構築 `C(a1, ..., an)` は、関数 `c_new(a1, ..., an)` の呼び出しになる（関数名は構築子の名前の小文字と `_new`。
  名前が重なれば番号を付ける）。引数のない構築子は `[k]` の定数になる。
- `match` は、先頭の番号 `rec_at(s, 0)` と比べる `if` の連鎖になる。最後の枝（`_` があれば `_` の枝）が残りの場合を
  受け持つ。枝の束縛は、項を先頭から順に取り出す `let` になる（`rec_at`、`rec_take`、`rec_drop` で長さと中身を読む）。
- 補助関数は LPTL の関数として書き、型検査を通す。`rec_drop(xs, n)` は先頭 `n` 個を除いた残り、`rec_take(xs, n)` は
  先頭 `n` 個、`rec_at(xs, i)` は `i` 番目（0 から。範囲外は 0）。どれも `fold` と組み込みの関数だけで書く。
- 構築の関数と補助関数には `W-UNUSED-FUNCTION` を出さない（使われなくても警告しない）。

`match` の規則は v1.4 と同じである。全部の構築子を一度ずつ書くか、最後に `_` を書く（網羅性）。同じ構築子の枝の
重複、`_` の後の枝、全部の場合を書いた後の `_` は誤り。枝の束縛の数は構築子の項の数と合わせる。

## 3a. 印つきの写し（型の区別）

再帰する型 `T` の宣言の順の番号を `r`（0 から）とする。`T` の印の型は、`Pair<Unit, Unit>` を `r` 段入れ子にしたものである
（`r = 0` は `Pair<Unit, Unit>`、`r = 1` は `Pair<Unit, Pair<Unit, Unit>>`）。印の値は `unit` の対の入れ子で、段数が違えば
別の型になる。

印つきの写しでは、

- 再帰する型 `T` の値の型は `Pair<印の型, List<Int>>` になる（`Tree` なら `Pair<Pair<Unit, Unit>, List<Int>>`）。
- 構築の関数は、印を付けた値を返す。引数のない構築子の値も同じく印を付ける。
- `match` は、対象を補助関数 `tree_flat`（型の名前を小文字にして `_flat` を付けたもの。`tree_flat(v) = snd(v)`）
  に通して中身の列を取り出す。この補助関数は番号 `r` の印の型の値だけを受け取るので、別の再帰する型の値を渡すと
  型検査が拒否する。
- 再帰する型の値を `List<Int>` の位置や別の再帰する型の位置に置くと、型検査が拒否する。

印なしの写しは、印を付けず §3 の符号化をそのまま使う。両方の写しは同じプログラムから作る。

## 4. 型

- **型の区別**：異なる再帰する型どうし（形が同じものも）は、混ぜると `E-TYPE-ARG` で拒否される。`List<Int>` の値を
  木の位置に渡すことも拒否される。判定は印つきの写しを検証済みの部品が検査して行う（§3a、§8）。
- **型エラーの文面**：印つきの型は、`Pair<…>` の形ではなく、再帰する型の名前（`Tree`）に直して出す。
- **既知の制限**：印は構造の型なので、利用者が印と同じ形の値（`pair(pair(unit, unit), list<Int>(0))` など）を組み立てると、
  印つきの写しは通る。その場合も印なしの写しの検査で拒否されるが、文面は内部の形（`List<Int>` と `Pair<…>`）で出る。
  名義の型にすれば、この穴は消える（§9）。
- `eq(a, b)` は値の列を構造で比べる。符号化は一つの値に一つなので、木の等しさとして正しい。印つきの写しでは、同じ再帰する型どうしの
  比較だけが型検査を通る。
- `Dict<K, V>`、`List<T>`、`Option<T>`、レコードの項などに再帰する型を使うのは通常どおりである（型の名前だけが書き換えられる）。

## 5. 入出力と実行

- `run`（`--plain` を含む）：再帰する型の入力と出力は、その値の整数の列（plain JSON の整数の配列）。例：`Leaf` は `[0]`、
  `Node(Leaf, 3, Leaf)` は `[1,1,0,1,3,1,0]`。木の形の JSON（`{"Node": [...]}`）は未対応（§9）。
- `tlvm exec`：entry の入力が再帰する型なら `UnsupportedEntry`（終了コード 64）。入力の型 `List<Int>` と同じ扱い。
  出力は `run` と同じく、整数の列を plain JSON で一行に書く。
- 資源の上限は v1.13 のまま（値の節点数の上限は `run --plain` の入力の上限）。

## 6. 停止

- 再帰する型を上から下へたどる関数は、再帰するので `rec fn` にする（v1.7 と同じ規則）。`rec fn` のあるプログラムは
  停止を保証しない（`"terminates":false`）。`rec fn` のない再帰は `E-CYCLE-CALL`。
- 補助関数と構築の関数は再帰しないので、停止は常に保証される。

## 7. 診断

新しく加えた診断：

| コード | 段階 | 意味 |
|---|---|---|
| `E-REC-FIELD-TYPE` | name | 再帰する型の項が `Int`、`Bool`、再帰する型そのもの以外（§2） |
| `E-REC-TYPE-PARAM` | name | 再帰する型に型引数を付けた宣言（§2） |

既存の診断を再利用する：`E-RECORD-DUPLICATE-TYPE`、`E-SUM-DUPLICATE-CTOR`、`E-SUM-NAME-CONFLICT`（束縛名を含む）、
`E-SUM-CTOR-ARITY`、`E-SUM-UNKNOWN-CTOR`、`E-MATCH-MISSING`、`E-MATCH-DUPLICATE`、`E-MATCH-UNREACHABLE`、
`E-MATCH-MIXED`、`E-TYPE-GENERIC-ARITY`。`E-RECORD-UNKNOWN-TYPE` は、循環しない前方参照に限って従来どおり出る
（循環する型は受理する）。型の区別による拒否（§4）は `E-TYPE-ARG` で出る。

## 8. 検証との関係

- 検証済みの部品（`verus/`）は変えない。Verus の結果は v1.13 と同じ（626 verified、0 errors）。
- 書き換えは `trust-boundary.toml` の `glue` に載せる（`crates/tlvm/src/recursive.rs`）。区別の判定は、印つきの写しを
  検証済みの部品が受理することで行う（`cross_check`）。実行は印なしの写しで行い、これも検証済みの部品が受理したものだけ。
- 符号化の誤り（長さの取り違えなど）は、検証済みの部品の受理では見つからない。`crates/tlvm/tests/recursive.rs` の実行の検査で確かめる。
- 型エラーの文面の名前への書き換えは接着部分である。受理の判定には使わない。

## 9. 次の課題（候補）

- 名義の型：型の名前を検証済みの型検査の核に入れる。核の型に名前を加えるので Verus の作業になる。v1.0.0 の前に決める。
- 木の形の JSON による入出力（`{"Node": [...]}`）。
- 項に `String`、`List`、レコード、再帰しない直和型を置くこと（符号化の拡張）。
- 総称の再帰する型（`type Tree<T> = ...`）。

## 10. LLM での確認

評価タスク `99-bst_height`（整数の列を二分探索木に挿入し、その高さを返す）を一つ、評価用の LLM で一回だけ確認した
（`--arms lptl`、`--rounds 1`、`--repeats 1`、修復なし）。`eval/SKILL.md` に「Recursive sum types」の節を加え、
`eval/manifest.json` を書き直した。結果は §11。
