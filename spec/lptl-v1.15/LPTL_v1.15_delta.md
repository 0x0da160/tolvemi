# LPTL v1.15 差分仕様：名義の型

本書は [v1.14 差分仕様](../lptl-v1.14/LPTL_v1.14_delta.md) に対する差分である。宣言した型（レコード型・直和型・再帰する直和型）を、展開後の構造が同じでも宣言の名前で区別する（名義の型）。v1.0.0 の仕様凍結の前に決める項目（v1.14 §9）。

状態：処理系は本書どおりに実装済み。LLM での確認は行わない（型検査の変更で、評価タスクは増やしていない）。

**検証済みの核（`verus/`）は変えない。** 型の名前は核の型に入れず、検査の前に接着部分（`crates/tlvm/src/nominal.rs`）で、検査用の写しに宣言ごとの印を付ける。

- **印つきの写し（検査用）**：宣言ごとの印を付けた同じプログラム。検証済みの部品がこの写しを検査し、拒否ならその診断を返す。
- **印なしの写し（実行用）**：v1.14 までと同じ展開。印つきの写しが受理されたときだけ、検証済みの部品が検査し、実行する。

**この版に含めないもの**：型の名前そのものを検証済みの核の型に入れること（§8）、印の形を手で組んだ値の文面（§5）。

## 1. 追加・変更するもの

- 宣言した型の等価性：宣言が同じものだけ等しい（§2）。
- 型エラーの文面：宣言の名前で出す（`A`、`Box<Int>`、`Tree`）。
- レコードと直和型の `fst`・`snd`：名義の型の値には使えない（§2。破壊的変更）。
- 新しい診断コードはない。既存の `E-TYPE-ARG`、`E-TYPE-FIELD-ACCESS`、`E-TYPE-MATCH-SCRUTINEE`、`E-TYPE-RETURN`、`E-TYPE-FST-ARG`、`E-TYPE-SND-ARG` を、名前つきの文面で出す。

## 2. 規則

- **宣言の番号 `r`**：レコード型・直和型・再帰する直和型の宣言の順（0 から）。同じ名前の二つ目以降は数えない（重複の診断は v1.4 と同じ）。
- **名義の区別**：二つの宣言の型どうしは、展開後の構造が同じでも別の型で、混ぜると拒否される。
  例：`type A = { x: Int }` と `type B = { z: Int }` で、`A` の引数に `B` の値を渡すと `E-TYPE-ARG`（期待 `A`、実際 `B`）。
- **総称の型**：宣言ごとに一つの印。型引数は型の中に残るので、`Box<Int>` と `Box<Bool>` は別の型になる。`Box<Int>` どうしは同じ型。
- **値の作り方**：名義の型の値は、宣言の名前による構築（`Box { ... }`、`Circle(2)`、`Leaf`）で作ったものに限る。`pair(...)` で組んだ値は、構造が合っても名義の型にならない（`E-TYPE-ARG`）。
- **`fst`・`snd`**：名義の型の値に使えない（`E-TYPE-FST-ARG`、`E-TYPE-SND-ARG`）。レコードの中身は `e.f`、直和型の中身は `match` で取り出す。
  v1.14 までは、レコードが展開後の pair だったので `fst` が型検査を通り、最初の field を返していた。v1.15 から使えない。
- **組込みの型**：`Pair`、`Option`、`Result`、`List`、`Dict` は宣言の名前を持たない。従来の規則で決まる。

## 3. 印と写し

印の型 `tag_r` は `Pair<Unit, Unit>` を `r` 段入れ子にした型である（`r = 0` は `Pair<Unit, Unit>`、`r = 1` は `Pair<Unit, Pair<Unit, Unit>>`）。印の値は `unit` の対の入れ子で、段数が違えば別の型になる。

印つきの写し（検査用）では、

- 宣言の型 `T` は `Pair<tag_r, S>` になる。`S` は展開後の構造（レコード型は field の pair の入れ子、直和型は `Result` の入れ子、再帰する直和型は `List<Int>`）。
- 構築 `T { ... }` と `C(...)` は、補助関数 `<名前>_wrap(x: S) -> T = pair(tag_r, x)` の呼び出しになる。引数のない構築子の値も印を付ける。
- field の参照 `e.f` と `match` は、印つきの型のまま検査する。型検査器は印の後ろの構造で field と枝を数える（`checker.rs`）。検証済みの部品へ渡す前に印を外す（`snd` を挿入する。`nominal::is_tagged`）。
- 印つきの型は、文面では型の名前に直す（§6）。

印なしの写し（実行用）は v1.14 までの展開のまま。印を付けない。

## 4. 検査の順

1. 印つきの写しを検証済みの部品が検査する。拒否なら、その診断を返す。
2. 受理なら、印なしの写しを検証済みの部品が検査する（v1.14 の経路）。
3. 両方が受理したプログラムだけを実行する。

## 5. 既知の制限

- **印の形を手で組んだ値**：`pair(pair(unit, unit), pair(x, 2))` のように印の形を手で書いた値は、印つきの写しを通ることがある。その場合も印なしの写しの検査で拒否される。型の保証は保たれるが、文面は期待の型を名前で、実際の型を構造で出す（`expected Box, actual Pair<Pair<Unit, Unit>, Pair<Int, Int>>`）。
- **二度の検査**：名義の型を一つでも含むプログラムは、印つきの写しと印なしの写しを二度検査する。コンパイルの時間は増える（速度の目標は §8）。
- **印の番号は接着部分の前提**：番号は `Tags::of` が宣言の順で一度だけ決める。二つの宣言に同じ番号が付けば、検証済みの部品は名義の区別を見落として、混ぜた値を受理する。実行は印なしの写しで、構造として型に合う値だけが動く（区別の保証の外）。

## 6. 実行と入出力

- 実行は印なしの写しで行う。値の表現、値 JSON、plain JSON、`tlvm exec`、資源の上限は v1.14 と同じ。
- 型エラーの文面：印つきの型は宣言の名前に直す（`api.rs` の `show_names`）。これは接着部分で、受理の判定には使わない。
- `tlvm check` の型の表示も、名前で出る。

## 7. 検証との関係

- 検証済みの核（`verus/`）は変えない。Verus の結果は v1.14 と同じ（626 verified、0 errors）。
- 印の付与と書き換えは接着部分（`trust-boundary.toml` の `glue`）：`crates/tlvm/src/nominal.rs`、`checker.rs`、`api.rs`、`records.rs`、`sums.rs`、`recursive.rs`。
- 印の付け方の誤り（同じ番号など）は、検証済みの部品の受理では見つからない。`crates/tlvm/tests/nominal.rs` の検査で確かめる。
- 名義の区別そのものは、印つきの写しを検証済みの部品が検査して判定する。

## 8. 次の課題（候補）

- 名義の型を検証済みの核に入れる（核の型に名前を加えるので Verus の作業になる）。今回は核を変えずに同じ区別を得たので、必要になったときだけ行う。
- 木の形の JSON による入出力、項に `String`・`List`・レコード・再帰しない直和型を置くこと、総称の再帰する型（v1.14 §9 と同じ）。
- v1.0.0 の前に残る課題（本書の外）：パッケージ管理（設計が必要）、速度の目標（計測の基準だけがある）。

## 9. 結果

- `crates/tlvm/src/nominal.rs`（新規）：宣言の番号、印の型と値、名前つきの型、`<名前>_wrap` の補助関数、`is_tagged`。

- `crates/tlvm/src/checker.rs`：印の後ろの構造で field と枝を数える。名義の型に `fst`・`snd` を使わせない。
- `crates/tlvm/src/api.rs`：`compile_nominal`。印つきの写しを先に検査し、拒否なら名前に直した診断を返す。受理なら印なしの写しを検査して実行する。
- `crates/tlvm/tests/nominal.rs`（新規、12 件）：同じ形の別の型の拒否、構造だけの値の拒否、総称の型の区別、手で組んだ印の拒否、field の参照と `match` の拒否、`fst`・`snd` の拒否、入れ子の型の名前、レコード更新と直和型の実行。

- `cargo test --release --locked --no-fail-fast` は 250 件すべて成功（v1.14 の 238 件に、nominal の 12 件を加えた）。`python3 eval/check.py`（99 タスク、SKILL.md の例 17 個）、eval の単体試験、`examples/*.tlvm` の `tlvm check` も成功。
